# Maestro 用户体验深度分析

> 版本 v1.0 · 2026-09-25
> 方法：沿「派活 → 等待 → 回顾 → 纠偏 → 长期相处」五个阶段推演用户旅程，找出焦虑点与摩擦点
> 结论将回写 [DEV_PLAN.md](./DEV_PLAN.md) 新增 U 组（体验层重大改进）

---

## 〇、核心洞察：自主 Agent 产品的本质是「信任管理」

用户把工作交给 AI 的每一刻，心里都在问三个问题：

1. **交出去之前**：「它理解对了吗？会花多少钱？」（信心）
2. **跑的过程中**：「它在正轨上吗？走偏了我能及时拦住吗？」（掌控感）
3. **拿到结果后**：「我能快速验证它没骗我吗？错了能低成本挽回吗？」（可验证与可恢复）

**所有 UX 决策的检验标准：它是在积累信任还是在消耗信任。** 由此推导出八个重大改进方向，按旅程阶段排列。

---

## 一、派活阶段：把「输入任务」的摩擦降到零

### U1. 全渠道任务入口（Task Inbox）

**痛点**：真实的任务从来不是在 Maestro 输入框里诞生的——它是一个失败的 CI、一条 GitHub issue、一张 bug 截图、同事消息里的一段话、晚上 11 点的一个念头。现在用户要：看到问题 → 打开 Maestro → 复制粘贴上下文 → 手动补描述。每一步都在流失。

**改进**：
- **全局快捷输入**（Raycast 式）：任意应用内 `Alt+M` 唤起输入条，粘贴即走，自动识别剪贴板内容类型（错误日志/URL/截图/代码片段）并附为上下文
- **分享到 Maestro**：浏览器扩展（把网页/issue 一键转为任务）、IDE 插件（选中代码 → 派活）
- **GitHub webhook**：打 `maestro` 标签的 issue 自动生成任务（Server 版）；CI 失败自动建任务
- **邮件入口**（Server 版）：转发邮件到专属地址即建任务

**为什么重大**：派活摩擦决定产品使用频率。频率决定一切。

### U2. 零配置首跑 + 项目名片

**痛点**：新用户装完的第一个 10 分钟决定留存。当前计划假设用户有 API key、懂模型选择。真实情况：很多人卡在「选哪个模型」就流失了。

**改进**：
- **自动探测已有配置**：检测 `~/.claude`、`~/.codex`、环境变量里的 API key，一键导入，零输入开跑
- **首个任务模板**：安装完成页直接给三个示例任务（「分析这个仓库」「修复一个 failing test」），2 分钟内让用户看到产品价值
- **项目名片**（自动生成，成本≈0）：首次打开项目时后台做轻量索引（文件清单 + git log 摘要 + README 消化），生成一张「项目卡片」给 Planner 用。用户看到「Maestro 已经理解了你的项目」的瞬间，信任建立

## 二、等待阶段：从「状态」到「叙事」

### U3. 里程碑式进度叙事（不是 "working..."）

**痛点**：`working` 状态对信任毫无贡献。用户回来看一眼 "working"，既不知道方向对不对，也不知道还要多久。herdr 的状态汇总解决的是「监工效率」，没解决「掌控感」。

**改进**：
- 事件流自动升级为**人类可读的里程碑**：「已读完 auth 模块（12 文件）→ 定位到 bug：token 刷新竞态 → 正在写修复 + 回归测试 → 运行测试中」
- 实现方式：Worker 事件流每 N 个事件，用 L1 小模型压缩成一句话（每次几百 token，信任收益巨大——本身就是 Token 经济的合理支出）
- **进度条心理学**：给计划里的每个 todo 项配预估权重，进度条按完成度推进；ETA 用「同类任务历史时长」估算，标注置信度
- **成本实时可见**：任务进行中实时显示已花费 + 预估总花费（账本已有数据，只差呈现）

### U4. 飞行中转向（Steering）⭐ 交互层最大的创新机会

**痛点**：所有现有工具（herdr/Trae/Claude Code）都只有两个极端：等着（直到 blocked 或 done），或杀掉重跑。但真实的协作是：「看到它正要重构那个文件——等等，别动那个，只修 bug！」现在你只能眼睁睁看着它跑偏，或全部推翻。**这是自主 Agent 最大的信任杀手。**

**改进**：三档干预粒度——
1. **轻推（任意时刻）**：向运行中的任务发一条「补充指示」，排在下一个决策点生效（headless Worker 在步骤间生效）
2. **暂停对话（随时）**：任务暂停，进入对话——你告诉它哪里偏了，它消化后带着修正继续。这是「拉回正轨」而不是「推倒重来」
3. **接管（少见）**：切到逐步模式，人审批每一步，再放手回自主模式

**技术可行性**（诚实评估）：headless 外部 CLI 的 mid-run 干预粒度有限——「轻推」在 Worker 步骤间生效（P1 可做）；「暂停对话」在 P2 自研内置 Executor 上完整实现（我们拥有 agent 循环，想做多细做多细）。**这是内置 Executor 除了省 token 之外的第二个存在理由。**

**为什么重大**：这把「开环放权」变成「闭环协作」。类比：不是把车交给自动驾驶就锁车门，而是随时可以握方向盘。

## 三、回顾阶段：验收体验决定用户敢不敢派更重要的活

### U5. Diff 之外的验收面（Review Ergonomics）

**痛点**：任务完成后用户面对一堆 diff——但 diff 只回答「改了什么」，不回答「为什么改」「改得对不对」「我能只接受一半吗」。

**改进**：
- **一句话结果卡**：每个任务完成通知 = 结果摘要 + 验收门状态（测试通过 12/12）+ 花费 + 节省 + 「查看 diff」入口。让 80% 的场景在 5 秒内完成「扫一眼→放心」
- **变更叙事**：diff 上方一段话解释「为什么这么改」（从 Planner 汇总里提取，零额外成本）
- **hunk 级部分接受**：diff 按 hunk 拆分，可逐块接受/拒绝；拒绝的 hunk 附一句理由，自动转为修正任务回给 Worker。**拒绝不是终点，是下一轮输入**
- **非代码工件**：UI 任务附截图对比、测试任务附通过率变化、重构任务附性能对比

### U6. 失败体验：事后检讨 + 断点续跑

**痛点**：任务跑了 30 分钟失败，现在只有「failed」。用户最怕的不是失败，是「失败了要全部重来（再花一遍 token）」和「不知道为什么失败」。

**改进**：
- **人话检讨报告**：失败原因翻译成人类语言（「测试改了但 fixture 没更新，第 3 轮验证门没过」）+ 三个候选出路（换个思路重试 / 降级为人工 / 只保留已完成的部分）
- **断点续跑**：任务 DAG 的已完成节点不重跑，只重跑失败节点（事件溯源 + session ref 天然支持，P0 架构已铺路，只差 UX 呈现）
- **失败即学习**：失败原因写入项目记忆，同类任务下次自动规避（「上次这个项目 e2e 测试必须先起 docker」）

## 四、长期相处阶段：产品随使用变好，且用户看得见

### U7. 教学闭环（Feedback → Memory → 可见成长）

**痛点**：现有记忆系统（含 Trae 的）都是「隐性学习」——用户感受不到产品在变好，就没有养成粘性的理由。

**改进**：
- **显性反馈**：结果卡上的 👍/👎 + 一句话原因；拒绝 hunk 的理由——全部落入项目记忆
- **每周学习简报**：「本周我学会了：你的项目用 pnpm 不用 npm / 生成的代码要带中文注释 / 不要动 src/generated。本周为你省了 $4.2（62%）」——把隐性优化显性化，把省 token 卖点变成周常触达
- **偏好即配置**：累积的偏好可以查看、编辑、删除（用户对「AI 悄悄记着我什么」的知情权，也是对商业产品的道德差异）

### U8. 成本护栏（Spend Guardrails）

**痛点**：自主 Agent 的隐性心理障碍是「它会不会把我 API 余额烧光」。Token 账本解决了「看得见」，没解决「敢放手」。

**改进**：
- **计划审批门附带成本预估**：「此计划预估 $0.80（±30%），已按你的省钱策略路由」——审批时钱一目了然（预估 = 计划规模 × 路由档位，粗估即可，标注为估算）
- **预算三档**：宽松 / 标准 / 严格（严格=重要任务才升旗舰模型，其余 L1），用户可理解的语言而非模型名
- **月度预算软顶**：接近上限时通知并切换保守策略，绝不静默烧钱

### 第一部分对计划的两点修正（已回写 DEV_PLAN v2.1）

1. **内置 Executor（D2）的存在理由升级**：从「无外部 CLI 时的保底」升级为「飞行中转向（U4）+ mid-run 干预的完整实现载体」。这影响 P2 的优先级判断——它不是保底件，是体验差异化的关键件。
2. **「验收门」语义扩大**：从「防 Agent 谎报的机制」扩大为「用户验收体验的一部分」（U5），验收门的状态直接呈现在结果卡上，人机共用同一套验证标准。

# 第二部分：实际使用视角（U9~U14）

> v1.1 · 2026-09-25 增补
> 第一部分分析的是「单任务的信任旅程」；这一部分分析**任务之外的现实**——多任务并发、危机时刻、基础设施故障、人的作息、重复劳动。第一部分回答「敢不敢信任一个任务」，这一部分回答「敢不敢把它融进每天的工作流」。

## 七、方法：真实一天的推演

周三的普通一天：早上回来想看昨晚的任务跑到哪了；白天同时挂着 5 个任务、自己还在改代码；下午合上笔记本去开会；晚上 Anthropic 抽风返回 429；睡前想再派几个大活。推演这一天里所有「产品没有为此设计」的时刻，得到六个方向。

## 八、六个方向

### U9. 多任务噪音治理（day-2 留存问题）

**场景**：5 个任务并行——2 个重构、1 个安全扫描、1 个文档、1 个测试修复。通知每 3 分钟响一次：Worker 完成了一个子步骤、又拉起了一个终端、一条 lint 警告。用户把系统通知关掉——然后错过了真正需要他决策的 blocked。**信任闭环在通知疲劳里断裂：不是产品不好，是它太吵。**

**改进**：
- **通知分级**：只有三类值得打扰——blocked（需要你）、done（结果卡）、异常（failed/预算触顶）。其余进活动流不打扰（事件 schema 带 priority 字段，P0 埋点）
- **Digest 批处理**：低优先级通知聚合成「过去 30 分钟：文档任务完成 3 步，安全扫描进行中」一条
- **任务级静音**：「这个重构不用烦我，做完叫我」
- **深链直达**：点通知 → 直接落到那条 blocked 的决策界面，不是打开主窗口自己找（省 4 次点击 = 通知才有存在的意义）

### U10. 危机安全网：急停、时光机、禁区

**场景**：你瞥见 Worker 正在批量改 import——方向从 3 分钟前就错了，且已波及 20 个文件。此刻你需要：**立刻全停**（但保留现场，别 kill -9 什么都没了）、**看看它到底改了什么**、然后决定**整体回滚还是部分保留**。另一个场景：你正手动改 `src/auth.ts` 修急 bug，一个并行任务也在动这个文件——冲突在 5 分钟后爆发。

**改进**：
- **全局急停**：一键挂起所有 Worker（不是杀死——进程保活、现场保留），UI 明示「已暂停，现场完整，可逐个检视/回滚/恢复」
- **Checkpoint 时光机**：每个任务/每轮开始前自动 git 快照（worktree 架构下几乎零成本），UI 呈现为可回滚的时间线——「回到任务开始前」是用户听得懂的承诺
- **禁区（hands-off zone）**：编辑器插件/文件监听把「我正在编辑的文件」实时声明为禁区（E2 allowlist 的动态 deny 扩展），Worker 触碰即暂停询问

### U11. 基础设施现实：断连、故障、key

**场景一**：合上笔记本去开会。回来：WiFi 换了、IP 变了，3 个任务显示 `failed`——**但它们没有失败，只是断了**。错误的标签引发错误的用户行为（删任务重跑，再花一遍 token）。**场景二**：Anthropic 大范围 429/5xx，所有任务停摆——但用户明明还配了 OpenAI 和 Gemini。**场景三**：key 30 天前过期，今天才发现，跑了一早上的全是报错。

**改进**：
- **suspended ≠ failed**：断连/暂停是独立状态，网络恢复自动续跑（P0 daemon 的 session ref 恢复能力已具备，缺的是状态语义与感知）
- **Provider 故障切换**：429/5xx/超时自动路由到备用 provider 重试（T1 是成本轴，这是**可用性轴**，双轴同层）
- **key 生命周期**：有效性探测、过期前 7 天提醒、配额将尽 actionable 通知（点击直达设置页），错误信息永远带出路

### U12. 人的节律：隔夜摘要与错峰执行

**场景**：睡前派了 3 个不急的大任务。早上回来，想知道的只有三件事：**昨晚干成了什么、卡在哪、花了多少钱**——而不是翻 3 个任务的事件流。另一个被忽视的事实：**provider 有打折时段**（OpenAI Batch API 半价、Gemini off-peak 半价），可延后的任务挪到半价时段跑，是**零质量代价的省 token**——不降模型档位，只是挪时间。

**改进**：
- **隔夜/离开摘要**：「你不在的 9 小时：完成 2 个任务（diff 就绪待审），1 个卡在测试 fixture，花费 $1.2，比直连省 58%」——离开 N 小时后回来首屏呈现
- **定时任务**：cron 语义（「每周一 9 点：更新依赖跑全量测试，报告进收件箱」）
- **错峰执行（新 T6）**：任务标记「可延后」→ 自动排入 provider 折扣时段或 Batch API；审批门的成本预估直接标注「今晚半价时段跑省 $0.4」

### U13. maestro doctor：自诊断与第一天失败兜底

**场景**：新用户装好，跑第一个任务，报错 `connection refused`。他不知道是 daemon 没起、socket 权限、claude CLI 不在 PATH、还是 key 无效。翻文档 20 分钟 → 流失。**第一天的失败不是功能问题，是留存问题。**

**改进**：
- **`maestro doctor`**：一条命令全量自检——daemon 状态/socket/版本匹配/各 CLI 探测/key 有效性/磁盘空间，输出「哪坏了 + 怎么修 + 一键修复」
- **装机自检**：首次启动自动跑 doctor，问题在用户遇到之前呈现
- **错误 actionable 化**：所有基础设施错误带动作按钮（「打开设置」「换 key」「查看 doctor」），永远不让用户对着裸报错发呆

### U14. 重复劳动规模化：模板、任务即文件、批量

**场景**：维护 8 个微服务仓库，每次依赖爆 CVE 都要逐个打开跑同一条扫描命令。以及：新同事想要你调好的「升级依赖→跑测试→生成报告」任务序列，现在只能口头描述让他重调一遍。

**改进**：
- **任务模板**：参数化任务（`{repo}`、`{package}`），一键复用
- **任务即文件**：任务定义可导出为 `task.yaml` → 进 git → 团队共享 → 可审查可版本化（与 P3 Worker 市场同构，是它的本地版前奏）
- **跨项目批量**：「在所有标记为 `service` 的仓库跑安全扫描」（Server 版多租户之上的杀手级场景）

## 九、优先级与回写

| 方向 | 价值 | 成本 | 建议 |
|---|---|---|---|
| U9 通知治理 | ★★★★★（day-2 留存） | 低（分级+digest） | **P1 Sprint B**；priority 埋点进 P0 schema |
| U10 危机安全网 | ★★★★★（出事时的刹车） | 急停低 / 禁区中 | **急停 API 进 P0 schema，UI + checkpoint 进 P1 Sprint B**；禁区 P1.5 |
| U11 基础设施现实 | ★★★★☆ | suspended 语义低 / failover 中 | **suspended 语义进 P0 状态机**；failover + key 生命周期 P1 |
| U13 doctor | ★★★★☆（第一天留存） | 低 | **doctor 核心进 P0 CLI**；完整版（key/配额）P1 |
| U12 节律（摘要/排程/错峰） | ★★★★☆（省真金白银 + wow 时刻） | 中 | **P2**（digest 需事件数据累积；错峰 = T6 新机制） |
